## 审查清单

**代码质量：**
- 关注点分离清晰？
- 错误处理得当？
- 类型安全（如果适用）？
- 遵循 DRY 原则？
- 边缘情况处理了？

**架构：**
- 设计决策合理？
- 可扩展性考虑？
- 性能影响？
- 安全问题？

**测试：**
- 测试真正测试逻辑（不是 mocks）？
- 边缘情况覆盖了？
- 需要集成测试的地方有吗？
- 所有测试通过？

**需求：**
- 所有计划需求都满足了？
- 实现符合规范？
- 没有范围蔓延？
- 破坏性变更有文档？

**生产就绪性：**
- 迁移策略（如果有 schema 变更）？
- 考虑了向后兼容性？
- 文档完整？
- 没有明显 bug？

## 输出格式

### Strengths（优点）
[哪些做得好？要具体。]

### Issues（问题）

#### Critical（必须修复）
[Bug、安全问题、数据丢失风险、功能损坏]

#### Important（应该修复）
[架构问题、缺失功能、错误处理差、测试缺口]

#### Minor（锦上添花）
[代码风格、优化机会、文档改进]

**对于每个问题：**
- 文件:行号引用
- 哪里错了
- 为什么重要
- 如何修复（如果不明显）

### Recommendations（建议）
[代码质量、架构或流程改进]

### Assessment（评估）

**可以合并了吗？** [是/否/修复后]

**推理：** [1-2 句技术评估]

## 关键规则

**做：**
- 按实际严重性分类（不是所有都是 Critical）
- 要具体（文件:行，而不是模糊）
- 解释为什么问题重要
- 承认优点
- 给出明确结论

**不做：**
- 不检查就说"看起来不错"
- 把小问题标记为 Critical
- 对未审查的代码提供反馈
- 模糊（"改进错误处理"）
- 避免给出明确结论

## 示例输出

```
### Strengths
- 数据库 schema 干净，有适当的迁移 (db.ts:15-42)
- 测试覆盖全面（18个测试，所有边缘情况）
- 良好的错误处理和回退 (summarizer.ts:85-92)

### Issues

#### Important
1. **CLI 包装器缺少帮助文本**
   - 文件：index-conversations:1-31
   - 问题：没有 --help 标志，用户不会发现 --concurrency
   - 修复：添加带使用示例的 --help case

2. **缺少日期验证**
   - 文件：search.ts:25-27
   - 问题：无效日期静默返回无结果
   - 修复：验证 ISO 格式，抛出带示例的错误

#### Minor
1. **进度指示器**
   - 文件：indexer.ts:130
   - 问题：长时间操作没有 "X of Y" 计数器
   - 影响：用户不知道要等多久

### Recommendations
- 为用户体验添加进度报告
- 考虑配置文件以排除项目（可移植性）

### Assessment

**可以合并：修复后**

**推理：** 核心实现扎实，架构和测试良好。重要问题（帮助文本、日期验证）易于修复，不影响核心功能。
```
